README「設計の判断(5 つ)」の各項目について、さらに踏み込んだ検討 ── 採用しなかった案や、判断の細部 ── を残す。README は通読できる長さに保ち、ここに深さを逃がしている。

## 1. 動的 HITL ─ 「関連する指摘」を AI 自身に判断させる

ユーザーが却下・編集した指摘(seed)を起点に**関連する指摘だけ**を再分析するには、「関連」の判定基準が要る。本実装は **AI 自身に意味で判断させる**:

- AI に seed + 現状の ES 全文 + 全 suggestions を渡す
- AI が「ユーザーの操作の影響を受ける指摘」だけを意味的に選んで再評価する
- 影響を受けない指摘は触らない(サーバー側で温存)
- 過剰な再評価を prompt で明示的に抑制(「全部見直しではなく、操作の影響範囲に絞る」)

### なぜ構造的計算ではなく AI 判断か

「`related_suggestion_ids` を再帰深さ N で辿る + 物理近接 ±M 文字」という構造計算でも実装できたが:

- 深さ N / 近接 ±M の**数値が恣意的**(実測比較なしには根拠が出せない)
- 構造計算は AI の意味的判断より固い(関連を見落とす / 無関係を巻き込む)
- AI は「自己宣言し忘れた関連」も捕捉できる

トレードオフは AI 判断のレイテンシ + コスト増。だが HITL の本質(意味的な対話)には AI 判断方式が合致する。構造的制約とのハイブリッド化は v2 の余地。

## 2. モデル選択 ─ なぜ意味的差分判定だけ mini か

編集の「言い回しだけか / 主張が変わったか」の判定は:

- 入力 = 2 つの短い日本語文(編集前 / 編集後)、出力 = boolean + 一文の理由
- → full の能力(多段推論・長文構造把握・複雑な指示理解)を必要としない
- mini はコスト約 1/10・レイテンシ 1 秒未満。品質劣化リスクは「2 文比較」の単純さで吸収
- fail-safe: API 失敗時は「異なる」を返し、再評価を走らせる安全側に倒す

モデル比較の判定方法: 同じ ES に対する 3 モデルの出力を「症状診断の的確さ / 個性保護 / 削減提案の的確さ / 引用検証の厳密さ」の 4 観点で比較。ベンチは [`tests/analyze-bench.test.ts`](../tests/analyze-bench.test.ts)、出力サンプルは [`tests/output/`](../tests/output/)。

## 3. プロンプト設計の細部

### なぜ最大 15 件か

- HITL の総体性(個々の指摘が適切でも、全体として人間の判断品質を劣化させない)を考えると、1 セッションで判断できる指摘数には上限がある
- 経験則として 10〜20 件で判断疲労が顕著になる
- 15 件は「網羅的に出せるが、判断疲労を起こすほどは出さない」中央値
- ただし AI に「件数を埋めるな」と明示し、完成度の高い ES では 3〜5 件、未熟な ES では 12〜15 件、と **ES の複雑度に応じて変動**させる(硬直したヒューリスティックではない)

### なぜ数値スコアを表示しないか

- 採用担当が ES を読むのは「点数化のため」ではなく「人物像の把握のため」
- 数値で出すと、ユーザーは「点数を上げること」が目標になり、本来の目的(自分の人物像を表現する)から外れる
- 文章の価値を単一指標で潰すと、ES の本来の機能(複層的な自己表現)が失われる
- 内部の優先度には数値を使うが(`internal_priority`、UI 参照禁止)、画面へ渡るのは `display_priority`(high / medium / low の文字列)のみ。これも**ラベルとしては表示せず**、ハイライト背景の濃淡として控えめに反映するだけ(数値スコアも順位ラベルも画面には一切出さない)

## 4. 捏造防止 ─ なぜ三層必要か

| もし 1 層だけなら | 弱点 |
|---|---|
| 層 ① モデル品質だけ | モデル交換で崩れる |
| 層 ② 承認リスト注入だけ | 完全には弾けないケースが残る(リスト内の似た URL と勘違い 等) |
| 層 ③ Zod 検証だけ | 検出は後段で、AI が無駄に推論コストを使う |

**三層を組み合わせる**ことで、各層の欠点を他の層が補う。モデルを交換しても残る防衛になる。

- 層 ②「このリストの URL からのみ選べ」= 構造的制約 > prompt 指示(「捏造するな」は確率的に破られる)
- 層 ③ リトライは 1 回だけ(無限ループ防止)。通らなければ HTTP エラーでユーザーに通知し、**エラーを隠さない**

## 5. 書き込み型 UI の細部

### UI の各部位

| 部位 | 役割 |
|---|---|
| 上部 SummaryBar | 未処理 N 件を主役に + 採用 / 編集 / 自動修正 / 却下を控えめに並列 + 再分析ボタン |
| 中央 Canvas | ES 本文を大きく表示。薄い背景色 + 下線(error = red 実線 / convention = amber 実線 / alternative = blue 点線)。選択中は青系の ring。**本文ブロック上端に文字数(現在 / 上限)と字数削減アクション**。数値スコアは出さない |
| 右パネル 4 タブ | **指摘**(1 件詳細展開、元 / 提案の 2 ボックス対比)/ **企業要約**(価値観 + 採用基準 + 根拠リスト)/ **面接質問**(陳腐化通知 + 最新化)/ **履歴**(全操作の時系列 + 任意時点 revert) |
| 下部 総評 | summary + strengths + weaknesses + preserved_voice_note |
| 個別 revert | 処理済カードの「この操作を取り消す」(履歴タブと同じ store 経路) |

### なぜ「1 件詳細展開モード」か

- 1 件ずつ判断するリズムが判断疲労を抑える(フルリスト並列方式とは別軸の UX 哲学)
- 採用 / 却下 / 編集の直後に「次の最優先未処理」を自動選択し、「次へ」を毎回押す手間を消す
- 「全件を眺めたい」人には「全件一覧」ボタンで overlay 展開する保険を残す

### なぜ「履歴 review / revert」か

- HITL の哲学(個々の判断が適切でも、全体として判断品質を劣化させない)を保つには、**過去判断が常に再考可能**でなければならない
- Cmd+Z(直前 Undo)+ Cmd+Shift+Z(Redo)に加え、**任意の時間軸の判断を取り消せる履歴タブ**を用意
- 個別カードからの revert も履歴タブと**同じ store action** を呼ぶ。経路を一本化し「履歴と個別で挙動が違う」混乱を構造的に排除

### Cmd+Z と履歴 revert の使い分け

| 用途 | Cmd+Z(短期 Undo) | 履歴 revert(任意時間軸) |
|---|---|---|
| 直前操作の取り消し | ◯(連続押下で連鎖巻き戻し) | ◯(最新 entry をクリック) |
| 任意の過去判断の取り消し | ✕(順番にしか戻せない) | ◯(該当 entry を直接 revert) |
| 直接編集の取り消し | ◯ | ✕(v1 未対応、Cmd+Z で代替) |
| 結果 | 操作前の状態に完全復元 | 該当 suggestion を pending に戻す(再評価を促す) |

### 検討して不採用にした UI 案

| 案 | なぜ不採用にしたか |
|---|---|
| 完全 Word 校閲(中央も取り消し線 + 朱字) | 添削後の ES が視覚的に煩雑、長文で疲れる、最終提出物の可読性が落ちる(短期間試行したが、dogfood で「色使いが好きではない」と判明し撤回) |
| 右パネルのみ Word 校閲風 diff | 「右パネルでの斜線型も見にくい」と dogfood で判明し撤回 |
| 完全 Grammarly(対比表示なし) | 修正プロセスが見えず、教育的価値が低い |
| オーバーレイ展開(提案を主役、元は toggle) | ユーザーが「元と提案を**常時並列**で見たい」と明示、トグルが余計 |
| 文字単位 diff(GitHub 風) | 細かい変更には強いが、長文で noise、ES 添削にはやや過剰 |
| 余白コメント(margin にコメント) | v2 候補、初回提案外 |
| 手書き風フォント + 校正記号 | メタファが強すぎ、機械的な「校閲ツール」感が ES 添削に合わない |

中央 = Grammarly モデル(綺麗な提出物)、右パネル = シンプル並列(必要な対比のみ)、という**分業**に落ち着いた。

## 6. structural カテゴリ(実装済み・実験的)の詳細

当初は「部分指摘」(`original_span` で範囲を示し `proposed` で書き換え案)に限定していた。だが本来の添削は「冒頭が長すぎる」「結論が後ろすぎる」のような構造問題も含むため、`structural` カテゴリを追加した。**実装は済んでいるが実験的**な位置づけで(デモ動画では使っておらず、移動位置の粒度などに粗さが残る)、本格化は v2。

| operation | 内容 |
|---|---|
| `delete_paragraph` | 重複・冗長な段落の削除 |
| `reorder_paragraphs` | 段落の並べ替え(結論先出し / 整理) |
| `merge_paragraphs` | 冗長に分かれた段落の統合 |
| `move_sentence` | 文を別段落へ移動(位置ずれの修正) |
| `add_paragraph` | 欠落要素 / 企業接合パラグラフの追加 |

**HITL 維持の核**(「全面書き換え禁止」原則は保持):

- 各 structural は**指摘**として提示し、AI が直接書き換えない
- `lost_content` で「削除・統合で失うもの」を明示 → ユーザーが「原文の表現が消える」を意識して判断できる
- 派生 ES の preview は client 側で機械的に生成([`lib/state/structural_ops.ts`](../lib/state/structural_ops.ts))し、LLM の hallucination を避ける
- 採用は段落単位の操作を適用し、**Undo 可能**(各 structural = 1 履歴 entry)
- `add_paragraph` は v1 では**暫定実装**(schema 上 `new_content` は「追加方針(outline)」の短文)。採用後の本文品質はユーザー編集を前提とし、v2 では採用時に編集確認を挟んで AI の outline がそのまま提出文へ混入しない導線にする

## 7. テストデータ設計 ─ 2 軸 + 検証チェックリスト

5 本を 2 軸で配置:

| 軸 | 内容 |
|---|---|
| **AI の自制力** | 「直すべき ES」と「直すべきでない ES」の両極を含む |
| **企業情報の有無** | 企業価値ソースが機能する / しない両方をテスト |

### 5 本横断の検証チェックリスト

1. 完成度の高い ES に対して、AI が自制できるか(es1)
2. 内容の薄い ES に対して、網羅的に指摘できるか(es2)
3. 字数超過に対して、削減提案を出せるか(es4)
4. 個性を `preserved_voice_note` で認識し、保護できるか(es3)
5. 数字・時系列の矛盾を検出できるか(es5)
6. 企業情報から根拠を正しく抽出できるか(企業あり: es1 / es3)
7. 企業情報なしのとき、根拠を捏造しないか(企業なし: es2 / es4 / es5)
8. 添削条件の自由入力がユーザー意図として指摘に反映されるか(es3)
9. 15 件上限を超えそうな状況で優先度判断できるか(es2)
10. 動的 HITL: 採用 → 却下 → 編集 → 直接編集で、関連指摘が更新されるか(全 ES)
11. 逆質問 → 回答 → 回答を踏まえた提案、が成立するか(es2 / es4 / es5)
12. 数値スコアを一切出力しないか(全 ES)

各 ES の本文は [test_es_v1.md](test_es_v1.md)、操作の実演は [submission_walkthrough.md](submission_walkthrough.md)。
